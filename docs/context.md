## Key Design Decisions

### eBPF Architecture

**Perf event array, not ring buffer.** The C program uses
`BPF_MAP_TYPE_PERF_EVENT_ARRAY`. Ring buffer (`BPF_MAP_TYPE_RINGBUF`)
is preferred on kernels ≥ 5.8 and avoids event loss under load, but
migration requires changing both the C map definition and the Go
reader. Deferred to a future pass — everything else stays the same.

**Per-CPU heap maps for all structs.** eBPF stack is 512 bytes. All
event structs are larger. Per-CPU arrays provide scratch space with no
locking needed since each CPU core uses index 0 of its own copy.

**Kernel ≥ 5.11 target.** Uses `bpf_get_current_task_btf()` for
cleaner task struct reading via BTF CO-RE. Also uses
`BPF_CORE_READ` throughout. Would need fallback to
`bpf_probe_read_kernel` for older kernels.

**Explicit pad fields in all C structs.** Every struct has named
`_padN` fields where alignment gaps would otherwise exist. The Go
structs in `types.go` mirror these exactly including pad bytes.
`binary.Read` with `LittleEndian` deserializes directly — no manual
field extraction needed.

**Single perf output map, typed fan-out in Go.** The C program
writes all event types to one `events` perf array. The Go listener
reads raw bytes, peeks at the first 4 bytes for event type, then
`binary.Read`s the correct struct. The dispatcher fans out to typed
channels. This keeps the kernel side simple.

**Minimal kernel-side filtering.** Only genuinely high-volume events
are filtered in C (mmap/mprotect only on PROT_EXEC, openat only on
O_CREAT, socket only for SOCK_RAW/SOCK_PACKET, DNS only on port 53).
All other filtering happens in Go where it is easier to maintain and
change without recompiling the BPF object.

### Dispatcher Design

`PtraceEvent`, `CapsetEvent`, and `NamespaceEvent` are all translated
into `SecurityEvent` by the dispatcher before going on the Security
channel. This keeps the consumer (future security job) working with
one type rather than three. The original event type integer is
preserved in `SecurityEvent.Type` so the consumer knows what it got.

`DNSEvent` also goes to the Security channel (not Network) because DNS
is primarily useful for C2 detection. The parsed questions and answers
are serialized to JSON in `SecurityEvent.Details`.

Module events go to their own `Module` channel rather than Security
because they may eventually need YARA scanning of the module file,
similar to how file events need YARA.

### Scanner Pool

Two submission methods on purpose:

- `Submit()` — non-blocking, returns false if full. Used nowhere
  currently but kept for future callers that want to drop rather
  than wait (e.g. a periodic background scan that can afford to skip).
- `Enqueue()` — blocking on ctx, returns false only on cancellation.
  Used by file and process scanners where back-pressure is correct
  behaviour — the eBPF channel naturally buffers upstream.

Autotune runs every 10 seconds. Grows by one worker when queue depth
exceeds current worker count and headroom exists. Shrink logic is
written but commented — live shrink requires per-worker cancel
contexts, deferred to a future pass.

### File Scanner

Pipeline per event:

1. `ExclusionFilter.ShouldScan()` — path/extension/pattern rules
2. `isEligibleFile()` — size bounds (10 bytes–100 MB) + magic byte check
3. `RecentScanTracker` — 5 minute TTL dedup by QuickHash (first 8 KB)
4. `Pool.Enqueue()` — blocking submit, back-pressure propagates up
5. Result collection — same goroutine blocks on resultCh
6. `ClassifyYARASeverity()` — severity from match count and rule prefixes
7. Full SHA256 only computed for non-clean results
8. `FileQueries.Insert()`

Magic byte check covers: ELF (7f 45 4c 46), shebang (#!), PE (MZ),
Java class (ca fe ba be), Python bytecode (trailing 0x0d). Non-
executable files are skipped entirely — this is the most effective
noise filter for file-create events.

### Process Scanner

Pipeline per event:

1. `ProcessFilter.IsTrusted()` — skip configured process names
2. `resolveExePath()` — `/proc/PID/exe` first, absolute filename fallback
3. `RecentScanTracker` — 10 minute TTL dedup by exe path
4. `Pool.Enqueue()` — blocking submit
5. Result collection
6. `ClassifyYARASeverity()`
7. Full SHA256 only for non-clean results, stored in Notes field
8. `ProcessQueries.Insert()`

`resolveExePath` rules:

- `/proc/PID/exe` preferred always
- If stat fails on resolved path → debug log, return empty (AppImage
  FUSE mounts, user-namespace mounts)
- Fallback to `event.Filename` only if absolute AND stat succeeds
- Relative paths dropped (shell PATH resolution candidates)
- Non-existent absolute paths dropped (failed execve attempts)

### Severity Classification

`scanner.ClassifyYARASeverity()` in `internal/scanner/severity.go`.
Single function, shared by all scanners. Rules:

- 0 matches → CLEAN
- Rule prefix `APT_` → CRITICAL
- Rule prefix `Ransomware` → CRITICAL
- Rule prefix `Exploit` → HIGH
- 3+ matches → HIGH
- 1-2 matches → MEDIUM

### Autorun Scanner

Runs on a ticker (default 30 min). On each cycle:

1. `GetSources()` returns all platform sources (Linux: 12 categories)
2. Each source runs concurrently, results merged
3. `Diff()` compares against in-memory state map
4. New entries → `Insert()` + WARN log
5. Removed entries → `MarkInactive()` + WARN log
6. Existing entries → `UpdateLastSeen()`

Deduplication key: SHA256 if available, otherwise
`category|location|image_path`. State is loaded from DB on startup
via `LoadActive()`.

### SQLite Configuration

WAL mode, synchronous=NORMAL, cache=10000 pages, temp_store=MEMORY,
foreign_keys=ON. Single writer connection (`SetMaxOpenConns(1)`).
Read-only consumers (future Wails UI) use `OpenReadOnly()` with
`file:path?mode=ro&_journal_mode=WAL`.

All queries built with `github.com/Masterminds/squirrel`. No raw SQL
strings in query files except schema DDL in `migrate()`.

### Channel Buffer Sizing

All channels (rawCh, and each typed channel in `Channels`) use
`cfg.PerformanceSettings.ScanQueueSize` as buffer depth (default 1000).
This matches the YARA pool queue size so neither side applies
unwanted back-pressure on the other under normal load.

### Shutdown Sequence

1. Signal received → `cancel()` called
2. All goroutines select on `ctx.Done()` and return
3. `listener.Stop()` closes perf reader → `readLoop` exits on `ErrClosed`
4. `pool.Stop()` cancels pool context → workers drain and exit
5. `wg.Wait()` blocks until all goroutines confirm exit
6. Timeout enforced by `ShutdownTimeoutSec` (default 30s)

## What Needs To Be Written Next

### Immediate — Event Sink Job

`internal/jobs/eventsink.go` — consumes Network, Memory, Security,
and Module channels and writes straight to DB. No YARA. Once this
exists, remove the corresponding drain calls from `drainer.go`.
Delete `drainer.go` entirely when all five channels have real consumers.

Structure per channel:

- Network → `NetworkQueries.Insert()` — translate `ebpf.NetworkEvent`
  to `models.NetworkEvent`
- Memory → `MemoryQueries.Insert()` — translate `ebpf.MmapEvent`
  to `models.MemoryEvent`
- Security → `SecurityQueries.Insert()` — translate
  `ebpf.SecurityEvent` to `models.SecurityEvent`
- Module → `SecurityQueries.Insert()` — module loads are security
  events, store in security_events table

- `HashAnalyzer` — SHA256 lookup against known-malicious table
- `SigmaAnalyzer` — for log events (Phase 5)

circuit on first CRITICAL result (skip YARA if hash matches known-bad).

### Near Term — Running Process Scanner

On startup: walk `/proc/*/exe`, resolve each symlink, submit to YARA
pool. Periodic re-scan on configurable interval. Separate from the
eBPF process scanner which only catches new executions.

### Near Term — EventStatistic Aggregation Job

Hourly ticker. Queries each event table for counts grouped by
event_type and date. Upserts into `event_statistics` table.
Used by Wails dashboard — avoids expensive aggregation queries at
read time.

### Near Term — Pre-execution Autorun YARA Scan

After `Diff()` finds a new autorun entry, submit the `ImagePath`
to the YARA pool before inserting. Attach matches to the autorun
record. Requires adding `YaraMatches` field to `AutorunEntry` and
a corresponding column to the autoruns table.

### Future — Wails UI

Separate binary. Opens DB with `db.OpenReadOnly()`. Reads from all
query layers. Does not share any in-process state with the agent.
Model layer is already stable enough to start.

## Model Notes

`ProcessScanResult.Notes` currently stores the SHA256 hash of the
scanned binary for non-clean results. This is a temporary reuse of
the Notes field. When models are next revised, add `FileHash string`
to `ProcessScanResult` and a corresponding column migration.

`EventStatistic` table exists in schema but nothing writes to it yet.

`QuarantinedFile` table exists in schema but the quarantine workflow
(move, lock, restore) is not implemented.

## Known Limitations

1. mmap/mprotect event volume — fires on every shared library load
   and JIT compile. Memory channel drainer handles this for now.
   Consider rate-limiting per PID in the dispatcher or demoting to
   a sampling mode once the event sink job exists and real volume
   is measurable.

2. execve args — only `argv[1]` captured in C due to eBPF verifier
   loop restrictions. Full cmdline available from `/proc/PID/cmdline`
   in Go — the process scanner could read it there instead.

3. cwd in ProcessEvent — `emit_process_event` reads `dentry->d_name`
   which gives only the last path component, not the full path.
   Resolved in Go via `/proc/PID/cwd` symlink read. Currently the
   CWD field in the event is unreliable — use `/proc/PID/cwd` at
   the Go consumer layer.

4. Live worker shrink in Pool — the autotune `adjust()` function logs
   that it would shrink but does not actually shrink. Proper shrink
   requires per-worker cancel contexts. Low priority.

5. DNS on sendmsg reads `msg->msg_name` via `bpf_probe_read_kernel`
   but msg_name is a userspace pointer. Should be
   `bpf_probe_read_user`. Low risk (most DNS goes via sendto) but
   worth fixing.
